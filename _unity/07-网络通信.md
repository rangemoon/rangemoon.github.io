## 状态同步
### 概念
1. 通过网络将游戏对象的关键属性(位置、血量、动作等)从服务器同步到所有客户端，确保所有玩家看到的游戏状态一致

### 核心思想
1. 服务器"权威"，客户端只负责显示
2. 适合对实时性要求不苛刻的游戏(如MMORPG、沙盒游戏)

### 状态同步的实现
1. 网络框架选择
- 服务器/客户端模式：服务器管理所有状态，客户端是负责接受(防作弊强)
- P2P模式：玩家直接互传状态(适合小游戏，如联机游戏)
2. 核心组件：unity提供以下工具实现状态同步
- NetworkIdenetity：标记需要同步的游戏对象
- NetworkTransform：自动同步物体的位置/旋转
- SyncVar：同步脚本中的变量(如血量、分数等)

    ```Csharp
    using Unity.Netcode;
    public class PlayerHealth : NetworkBehaviour {
        [SyncVar]
        public int currentHealth = 100;

        [Server]
        public void TakeDamage(int damage) {
            if (currentHealth < 0) {
                currentHealth = 0;
                return;
            }
            currentHealth -= Damage;
        }
    }
    ```

3. 状态插值优化：直接更新位置会导致"跳跃"，需要平滑过渡
    ```Csharp
    // 平滑移动其他玩家角色
    void Update() {
        if (!IsOwner) {
            transform.position = Vector3.Lerp(transform.position, 
            targetPosition, Time.deltaTime * 10f);
        }
    }
    ```

### 优化
1. 带宽优化
- 只同步变化数据(如位置仅传X/Z, Y轴通过重力计算)
- 压缩浮点数(如位置精度保留2位小数)
2. 延迟处理
- 客户端预测：本地选移动，服务器修正(如FPS游戏)
- 缓存历史状态：丢包时用旧数据插值
3. AOI(只同步玩家周围的物体状态)

## 帧同步
1. unity种田的帧同步(Frame Synchronization)是一种多人在线的同步技术，其核心目标是确保所有客户端在同一逻辑帧上执行相同的操作，从而保证游戏状态的一致性。
2. 基础流程
- 输入同步：所有客户端将操作指令(如案件、技能释放)发送到服务器，服务器按帧号排序后广播
- 逻辑一致性：每个客户端基于相同的输入和初始状态独立计算，确保结果一致
3. 与状态同步相比
- 帧同步：传输操作指令(如按下A键)，客户端本地计算状态
- 状态同步：直接传输状态数据(如玩家坐标(20, 20))

### 帧同步实现
1. 网络框架选择
- 服务器模式(推荐)：服务器收集所有输入后按帧号广播，确保执行顺序一致
2. 帧率控制和输入同步
    ```CSharp
    public class FrameSync : MonoBehaviour {
        private const int TARGET_FPS = 30; // 逻辑帧率
        private float frameInterval;
        private int currentFrame;
        private Queue<InputData> inputQueue = new Queue<InputData();

        void Start() {
            frameInterval = 1 / TARGET_FPS;
            StartCoroutine(SyncFrames());
        }

        IEnumerator SyncFrames() {
            while (true) {
                // 1. 采集输入
                InputData input = GatherInput();
                inputQueue.Enqueue(input);

                // 2. 发丝部分输入到服务器
                SendInputToServer(input);

                // 3. 执行逻辑帧
                ExecuteFrame(inputQueue.Dequeue());

                yield return new WaitForSeconds(frameInterval);
            }
        }
    }
    ```

### 优化技术
1. 客户端预测：本地先执行输入，服务器校正回溯重演
2. 插值渲染：逻辑帧(30fps)与渲染帧(60fps)分离，通过插值平滑显示
3. 网络延迟
- 预测+补偿：客户端预测移动，服务器修正时插值过渡
- UDP协议：优先使用UDP减少延迟(需自定义可靠性层)
4. 浮点数差异：避免不同硬件浮点数精度误差导致不同步(定点数计算)

## 网络同步
1. 网络同步和延迟问题怎么解决？
- 网络同步延迟，我们首先要搞清楚，游戏采用的是帧同步还是状态同步
- 如果是状态同步：那么要解决网络延迟问题，只能通过传输来解决，一般用可靠的UDP来做，比如KPC等。减少网络延迟和网络波对游戏的体验。由于状态同步是服务器跑逻辑，客户端根据状态来展示，所以除了底层通过可靠UDP来减少网络延迟以外，没有其他办法。
- 如果是帧同步：每一帧，服务端会把所有客户端的操作转发出去，这个时候要解决网络延迟问题，也是用UDP来替代传统的TCP来做数据通信，如果某个数据包卡住，客户端可以用上一帧的操作，延长几帧的处理时间，做所谓"预演"。如果下一帧操作和上一帧操作一致，那么预演成功，客户端感觉不到卡顿；如果不成功，则会出现卡顿现象。

## TCP粘包和拆包
### 概念
1. 在unity网络开发中，处理TCP粘包和拆包(半包)的问题是常见的
2. TCP协议是面向字节流的，它本身不保护消息边界
- 粘包：发送发快速连续发送多条消息(如"Hello"和"World")，在接受方的缓冲区被合并成了一个大的数据块(合并成"HelloWorld")
- 拆包(半包)：一条完整的消息由于网络或缓冲区等原因，被分割成多个部分到达接收方
- 问题的根源是：TCP协议保证数据可靠有序传输，但不关心应用层消息的划分，发送和接受的数据量可能不匹配

### 解决方法
解决问题的核心思路在于：在应用层为数据流定义明确的消息边界
1. 长度信息法(最常用)：每条消息前附加一个固定长度的消息头(通常用2字节的int16或者4字节的int32)用来指示后面消息体的实际长度
2. 固定长度法：强制规定所有消息都必须完全长度相同。不足部分用特定填充字符补充。这种方式简单但是浪费带宽，灵活性差，一般不推荐用于游戏等可变消息长度的场景。
3. 结束分割符法：每条消息末尾添加一个结束分隔符(如换行符\n或自定义字符)。接收方根据这个分割符来拆分消息。缺点是，如果消息体本身包含结束符，需要做转义处理，增加复杂度。
- 对于unity中的socket通信，**长度信息法**因其高效和可靠性成为最常用和实践的方法.

## UDP/TCP/Websocket/KCP
### WebSocket(基于TCP) 
1. WebSocket协议的工作原理分为握手和数据传输两个阶段：
- 握手阶段：客户端通过HTTP请求与WebSocket服务器协商升级协议。客户端发起的WebSocket连接报文类似传统HTTP报文，其中包含Upgrade: websocket和Connection: Upgrade等字段。服务器收到请求后，返回101 Switching Protocols状态码，表示协议切换成功。
- 数据传输阶段：握手成功后，数据直接通过TCP通道传输，不再依赖HTTP协议。WebSocket协议的数据帧格式定义了标识、操作代码、掩码、数据、数据长度等字段。

```
客户端 GET /chat  Upgrade: websocket
服务器 101 Switching Protocols
之后：双方发 WebSocket 帧（有头、有长度，应用层消息是有边界的）
```
2. WebSocket协议是一种网络通信协议，旨在实现浏览器与服务器之间的实时双向通信。

### TCP
1. 传输控制协议：面向连接、传输可靠(保证数据正确性)、有序(保证数据顺序)、传输大量数据(流模式)、速度慢、每一条TCP连接只能点到点

### UDP
1. 用户数据报协议：面向无连接、传输不可靠(可能丢包)、无序、传输少量数据(数据报模式)、速度快，对系统资源的要求少，程序结构简单。
- UDP支持一对一，一对多，多对一和多对多的交互通信
2. UDP数据丢包，什么原因，怎么处理？
原因：
    - 接收端处理延迟
    - 数据包过大
    - 发送速率过快
    - 网络环境问题
    - 分片丢失
优化和解决方法：
    - 应用层重传机制：在应用层协议中增加确认和超时重发机制，使UDP传世更可靠
    - 调整缓冲区：增大接受端socket缓冲区，减少因缓冲区满导致的丢包
    - 控制包大小和发送速率：确保每个包小于MTU，并避免发送过快
    - 多线程或异步处理：接受和处理分离，减少延迟造成的丢包

### kcp
- Mirror 的传输是 KCP。KCP 是在 UDP 上做确认和重传的可靠层，用来保证消息按序到达。
